## 2. Railway model service

Create a Railway service from this GitHub repository and select branch `codex/rival-model-product`. In the service settings, leave **Root Directory** blank (repository root), select the **Dockerfile** builder, and set **Dockerfile Path** to `models/service/Dockerfile`. Railway also accepts the service variable `RAILWAY_DOCKERFILE_PATH=models/service/Dockerfile` for that path. Do not set a custom build or start command; the Dockerfile starts `python -m service`, which listens on Railway's `PORT`. If Railway builds the Next.js app or reports missing `models/service/requirements.txt` or `models/release-bundle`, check the branch, root directory, and Dockerfile path first.

Use GitHub-connected deployment for this service. The committed `models/release-bundle/` contains the selected model's runtime files; it contains no training archive. Railway needs enough memory for CPU PyTorch and the loaded model. Set `MODEL_SERVICE_TOKEN` to a long random value in Railway variables. Set the service healthcheck path to `/ready`, generate a public HTTPS domain, and copy its base URL. The current model service URL is `https://crl-head-to-head-production-12d1.up.railway.app`. Its domain targets the Railway-provided app port 8080. Check `GET /ready` after startup; it should report model version `20260921T223438Z`. The model endpoints require the bearer token and should not be called directly from browser code.

When promoting a new model, export and validate its bundle, replace `models/release-bundle/`, and commit it with the code that supports its schema. Retain the previous release for rollback. Do not copy raw match archives, `.env` files, or service credentials into the bundle.

## 5. Persistent history and matchup skill

Set `MATCH_HISTORY_ENABLED=1` only in the deployed web environment after signed-in integration passes. Manual **Sync Battles** and the live Vercel nightly sync capture the account owner's eligible standard-deck 1v1 matches and fetch each tracked friend's recent log. The archive retains at most the newest 100 full match rows per owner/player tag and per tracked-friend relationship. Compact per-deck totals, latest observed deck snapshots, and first/last seen times continue while tracking exists; the top five decks and counts are cumulative since tracking began. These are not lifetime game totals before tracking. Removing a friend deletes that relationship's history and deck totals; deleting an account deletes its archive. Collection includes reviewed constructed modes such as modern Classic/Grand Challenge event decks; draft, 2v2, modified decks, and malformed records are excluded. The short API log cannot recover older games that have already rolled off before capture starts, and nightly polling can miss games during high activity. The separate local research ingestion job remains paused; do not change the live nightly Vercel sync when managing that local job.

The website calculates model-relative skill across eligible standard 1v1 records, including Ladder, Ranked, and eligible Classic/Grand Challenge matches, after the model's training cutoff. Decisive eligible results contribute to the record; only supported deck pairs receive a modeled estimate, and draws are excluded from score estimates. Stored predictions include model version and cutoff; versions are not mixed. No outcome is sent to the predictor. The score uses the newest 100 full captured games; compact deck totals continue beyond this window. The current model-backed score is `50 + 100 × (actualWins − expectedWins) / scoredMatches`, bounded to 0–100; a separate recent-record score is used when no supported predictions exist. A score of 50 means performance matches deck-model expectations. Small samples can move the score sharply and are labeled provisional. Tough-matchup wins are wins with model probability below 40%.

This is a model-relative performance measure, not a pure causal skill rating. It does not account for opponent skill, matchup familiarity, or future balance changes, and it leaves the existing Elo rating intact. Supabase policies and grants passed catalog verification; real signed-in integration still needs testing before the feature flags are enabled.
